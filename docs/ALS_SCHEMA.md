# The Live schema as the contract of the `.als`

Material: Live 12 Suite installed (`C:\ProgramData\Ableton\Live 12 Suite`), build `12.0_12402`. Specimen: `templates/live12.als`, recorded by Live 12.4.5b11. Snapshot: `resources/live_schema/12.0_12402.txt.gz`, sha256 of the content `b7c9d4c767d8ca9b346ce7d517265446bbacd6de366cc058e155613789d0f299`.

The same digest was measured in the file installed at `C:\ProgramData\Ableton\Live 12 Suite\Resources\Schema\12.0_12402.txt`: the snapshot is a copy of the vendor, not a rewrite.

**The schema changes between builds, and fast.** Between `12.0_12000` and `12.0_12402` **922** fields appeared and **42** disappeared (2,886 to 3,766 fields, 364 to 412 classes). This is why the snapshot is per build and the `MinorVersion` the `.als` itself declares is the matching key. The `SchemaChangeCount` of the `.als` matches the `ChangeCount` of the schema of the same build, and the test `test_o_schema_descreve_o_build_do_template` measures that match.

---

## 1. What was measured

The Live publishes, in `Resources/Schema/<MinorVersion>.txt`, the schema of **its own object model**: 412 classes and 3,766 **distinct field names**, with the value class and the type of each field. Because the same name is declared by several classes, the total of **(class, field) declarations** is **7,943**. The two counts are different and both are measured: the first is `len(schema.elementos)`, the second is `schema.declaracoes()`.

That file is the **second authority** of the `.als`, beside the template (the specimen recorded by Live). The template shows what Live recorded; the schema declares classes and fields of the model. Neither of the two says what `aafton` writes: that is measured, apart.

The measurement has three parts:

1. **The snapshot matches the vendor.** The digest of the decompressed file is the one registered in
   `als_schema.SCHEMA_DIGEST` and the test `test_o_snapshot_bate_com_o_digest_do_vendor` fails
   when it diverges.
2. **The two eyes agree.** The template and the `.als` generated by `aafton` use **only**
   names that the schema declares, as a field or as a class. The only exception is the root of the
   document, `<Ableton>`, which is not part of the model. This is measured in
   `test_o_als_gerado_nao_usa_nome_fora_do_schema` and
   `test_o_template_tambem_so_usa_nomes_do_schema`.
3. **What the writer really writes.** For each selected concept, the path is classified against the **real output** of `aafton` (two minimal sessions written by the writer itself, with the template of the repository) and against the **controlled measurement** described in section 3.

The command that produces the table is:

```
.venv\Scripts\python.exe scripts\audit_als_schema.py
```

To export only the table to another file:

```
.venv\Scripts\python.exe scripts\audit_als_schema.py --markdown ALS_SCHEMA_TABLE.md
```

## 2. The model and the XML are different things

The schema describes the **object model** of Live: a tree of classes, in which each field declares the class of its value. `<AudioClip>` declares 51 fields, and the field `Fades` points to the class `ClipFades`, which in turn declares 10 fields. The resolver walks the path in that direction and returns the class of the value of the leaf.

The `.als`, on the other hand, is the **serialization** of that model, and not every field becomes a child element. The case measured here is the `Time` of the clip: the schema declares it as a field of class `Double`, and the `.als` writes the value in the **attribute `@Time`** of the `<AudioClip>` itself, not in a `<Time>` element. The template brings `@Time` in the `<AudioClip>` and no `<Time>` element in it; the `.als` generated by `aafton` brings the same attribute.

This is why the audit keeps the two things apart:

- the **path resolution** (`SchemaLive.resolver`) resolves the model path and only resolves when the schema declares every segment, and, when the segment names a list item, when the measurement in the template proves the membership (section 2.1). There is no "runtime tail": the contract is the whole schema.
- the **serialization mapping** (`als_schema.ATRIBUTOS_XML` and `als_schema.destino_xml`) is explicit and short: it says that `AudioClip/Time` becomes the attribute `@Time`. The table of the audit shows the two columns, `path in the model` and `serialization`, so that nobody confuses "the model declares this field" with "the `.als` has an element with this name".

### 2.1 List item: the name alone does not authorize

The schema declares that a field is a list; it **does not** declare which classes can be items of it. The resolver cannot accept any class name after a list: `AutomationEnvelopes/Envelopes/LiveSet/SmpteFormat` does not resolve, even with `LiveSet` being a class of the schema.

Who answers is the measurement in the template of the pinned build. The record `als_schema.LISTAS_MEDIDAS` keeps, for each list, the classes that the template shows as items:

| list field (class that declares it) | items measured in the template |
| --- | --- |
| `AutomationEnvelopes/Envelopes` | `AutomationEnvelope` |
| `ListAutomation/Events` | `EnumEvent`, `FloatEvent` |
| `LiveSet/Tracks` | `GroupTrack`, `AudioTrack`, `ReturnTrack` |

This is **empirical evidence of the second authority**, not information from the vendor: the `Resources/Schema` of Live does not bring that information. The record holds only for the measured build (`12.0_12402`, the `TranslatorNumber` of the schema); a schema of another build does not inherit it, and the resolver returns `None` for the item.

`None` means that **the schema-template contract does not prove** the path. It does not mean that Live refuses the path: it is a lack of proof, not an impossibility. The test `tests/unit/test_als_schema_lists.py` inspects the real template, at the explicit places of the table above, and checks the record against it.

## 3. The controlled sample and what "written" means

The audit writes **two** sessions with `aafton` itself, from the template of the repository, and measures the generated `.als`. The two inputs are controlled: they change the position of the clip, the duration, the offset in the source, the pan and the gains, and all the values are different from the ones the template brings. The origin of the timeline stays fixed at one hour (172,800,000 samples at 48 kHz) and the BPM is 60, so that the position in beats is the exact ratio of samples.

| | input A | input B |
| --- | --- | --- |
| track pan | 0.25 | 0.75 |
| track static gain | 0.625 | 0.25 |
| clip static gain | 0.375 | 0.625 |
| clip start | 7 beats (336,000 samples) | 11 beats (528,000 samples) |
| clip duration | 10 beats (480,000 samples) | 12.5 beats (600,000 samples) |
| offset in the source | 1.25 beats (60,000 samples) | 2.5 beats (120,000 samples) |
| gain points | (7, 1.0) and (10, 0.5) | (11, 0.25) and (12.5, 0.75) |

A path is classified as `written` only when the proof closes in three points:

1. the value **measured** in the generated `.als` matches the value **expected** from the input,
   in the two inputs;
2. the two inputs produce **different values**, so that the value comes from the input and not
   from a constant;
3. the measured value is **different** from what the template already had at the same path, so that the
   write changed the file.

The expected value of the position is computed by the sample ratio (`samples x bpm / (60 x rate)`), and not by the clip grid of Live: the expectation of the test is independent of the writer.

What **does not** prove a write:

- **declaring** the path in `als_paths` (the `declared` column of the table is that declaration, and
  it is a column of its own);
- **the path existing** in the generated `.als`. That proves presence, not a write: the value may have
  come from the cloning of the template. This is why the status of these paths is `present`, and not
  "inherited": inheriting from the template is not measured.

The 11 proofs of value, with the value measured in inputs A and B: track pan (`0.25`, `0.75`) and track gain (`0.625`, `0.25`); clip gain (`0.375`, `0.625`); clip start (`CurrentStart` and `@Time`: `7`, `11`) and end (`17`, `23.5`); offset in the source (`LoopStart`: `1.25`, `2.5`) and loop end (`LoopEnd`, `OutMarker`, `HiddenLoopEnd`: `11.25`, `15`); and the automation events (`(-63072000, 1), (7, 1), (10, 0.5)` and `(-63072000, 0.25), (11, 0.25), (12.5, 0.75)`).

The 12th measurement is an **integrity check**, and not a proof of a write: it checks that the `EnvelopeTarget/PointeeId` of the written envelope (100011) is equal to the `Id` of the `AutomationTarget` of the volume of the track itself (100011). Making the two Ids equal does not show that the writer wrote the path of the target: the `AutomationTarget` comes from the template, and the writer only **reads** its Id. This is why the check comes out as `integrity` and does not enter the list of proven paths: the volume target stays `present`, and not `written`.

The gain envelope is **new**: the template has no gain automation event on the track, and the `EnvelopeTarget/PointeeId` of the written envelope points to the `AutomationTarget` of the volume of the track itself. Without that link, the measured events would be of another curve.

The time of the sentinel (`-63072000`) is the value **observed in the pinned template**: the `FloatEvent` of `AutomationEnvelope/Automation/Events` carries `@Time="-63072000"`, and it is not a constant imported from the writer. If the writer changes the sentinel, the proof has to fail; if the expectation came from the writer, the measured and the expected would move together, and the proof would close without saying anything.

## 5. What the table shows

### 5.1 The measured coverage is smaller than the coverage of paths

Eleven paths were proven written: clip position (`@Time`, `CurrentStart`, `CurrentEnd`), offset and length in the source, static clip gain, track pan and gain, and the gain automation events with their time and value. The link of the envelope with the volume automation target is an **integrity check**, apart: it does not satisfy the same value proof that varies with the input, and that is why the volume `AutomationTarget` stays `present`, and not `written`.

Six concepts with an AAF counterpart **have no proven path**: `fades`, `marcadores`, `nome_da_faixa`, `midia`, `timecode` and `takes`. In those concepts the paths exist in the generated `.als`; some are declared by the writer, but **no measurement proves them**: the audit does not claim that the writer writes them, nor that Live uses them. That is a measurement gap, not a statement of absence, and that is what the `present` column means.

### 5.2 `takes`: structural availability, not semantics

The Live 12 model declares `AudioClip/TakeId` and `AudioTrack/TakeLanes`. That proves that the model has the concept; it does not prove how it maps the AAF. `aafton` writes each origin slot as an independent clip, and the measurement found no proven path of takes.

**Repeated media slots do not prove alternate takes.** Several clips that point to the same source are what the conversion produces when the AAF has more than one origin slot for the same material; saying that this "is a take" would be inferring semantics from structure. The correspondence between the AAF origin slot and the Live take remains open.

### 5.3 Split stereo pan: the structural basis exists, the behaviour was not verified

The mixer schema (`TrackDevice`) declares `PanMode`, `SplitStereoPanL` and `SplitStereoPanR` besides `Pan`. `aafton` writes only `Pan/Manual`, and that is what the measurement proves. This is the **structural** basis of the limitation registered in the README ("Exporting pan automation to AAF is supported only on mono tracks"): Live 12 has a split stereo pan in L and R, and the AAF has pan per channel.

**The behaviour of Live in that mode was not verified.** If the split `PanMode` carries the pan per channel of the AAF, or if Live ignores that path, only a real session in Live 12 answers. Until then, the limitation remains an implementation limitation of `aafton`, and the README should say that.

### 5.4 What the AAF does not carry, and what that does not prove

Track colour, quantisation, grid, warp, groove and plugin state appear in the table with `AAF counterpart = no`. That describes **the AAF model of this project**, which has no place to store those values; it is not a proof that the AAF specification could not carry them. The schema is the second structural authority of the `.als`; the table records only the measured sample of the writer.

Curve shape requires a contract and a proof of its own. This audit does not measure the fade round trip and does not support a universal impossibility in the AAF format.

### 5.5 The `Time` of the clip is an attribute, and `aafton` writes it

`AudioClip/Time` is declared in the schema (class `Double`) and **is** written: as the attribute `@Time` of the `<AudioClip>`, with the value of the clip position in beats. The earlier claim that "Live also does not write" the `Time` of the clip was wrong: the `<Time>` of the document are elements of `Locator`, `Breakpoint` and `RemoteableTimeSignature`, and the `Time` of the clip is an attribute. The measurement confirms the value: `@Time` follows `CurrentStart` (7 and 11 beats in inputs A and B).

## 6. Build, snapshot and the choice of the installed schema

The schema is per build, and the matching is checked **from the inside**: the `TranslatorNumber` of the schema has to be the suffix of the `MinorVersion` of the template (`12.0_12402` to `12402`), the `Version` of the schema has to be the `MajorVersion` of the template (`5`), and the `ChangeCount` of the schema has to be the `SchemaChangeCount` of the template (`5`). Internal metadata that is missing, in the template or in the schema, is also refused: a missing identity matches nothing. The **name of the file proves nothing**: a schema renamed to `12.0_12000.txt` still describes the build that its content declares, and the audit refuses it.

The audit refuses, with exit code **3**, a `--template` that does not match the selected schema: auditing a template of another build against this schema would say nothing about this one. The exit codes of the tool are: **0**, audit run and all the proofs closed; **2**, template missing or Live installed without `Resources/Schema`; **3**, the template does not match the selected schema; **4**, some measured proof did not close.

The search for the schema in the installation (`als_schema.schema_instalado`) searches **both** known roots before choosing, because the stable installation can be in the second and the beta in the first. Among the candidates, the **stable comes before the beta**, and the tie is broken by the normalized path, to make the choice deterministic given the same candidates.

## 7. Limits of this report

- The measured schema is from the build `12.0_12402`. Another build can declare other fields; the
  snapshot and the `MinorVersion` of the `.als` are the matching key.
- The list membership record (section 2.1) holds **only** for the build
  `12.0_12402`: it is a measurement of the template of that build, and not of the vendor schema.
- "present" means that the path exists in the generated `.als`; **not** that Live uses the
  value, nor that `aafton` wrote it. Confirming the behaviour requires opening it in Live.
- "written" means that the measurement proved the write **of that path, with that value**.
  It does not claim that the value is complete, correct for the use case, or that Live interprets
  it as expected.
- The catalogue holds selected concepts of the converter; it is not a complete inventory of the
  AAF. The schema has 412 classes, 3,766 field names and 7,943 class-field declarations: the
  audit covers the listed concepts, not the whole schema.
- The sample is minimal and mono (one track, one clip, one marker). Nothing here measures the
  behaviour of Live with a real session, nor with a stereo track.
- The native acceptance in Live 12 (opening the generated `.als`, confirming pan, fades, markers and
  automation) stays **pending**: nothing here replaces that evidence.
